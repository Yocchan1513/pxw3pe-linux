# 実機での測定結果(PX-W3PE Rev1.3、2026-10)

このブランチの変更の根拠になった測定のまとめ。

## 環境

- PX-W3PE(PCI `188b:5220`、subsystem `0b06:0001`、rev 01)。I2C は標準レイアウトで動作
- Celeron J2900、Ubuntu 24.04.3、カーネル 7.0.0-38-generic、IOMMU なし
- 地上波のみ(千葉、スカイツリー)。UHF 27ch の C/N は約 19 dB
- 取り込みは `tools/dvbtest.py`(B-CAS 復号なし)、検査は `tools/tsanalysis/tscheck.py`

## このドライバでの受信(このブランチの最終ビルド)

`insmod pxw3pe.ko adapter_nr=2,3,0,1`(ほかは既定値。DMA は ping-pong、8192 パケット × 2、MSI)。

- ロード: 鍵ファイルを読み込み、標準レイアウト、4/4 デモジュレータが応答、MSI、アダプタは S0 = 2、S1 = 3、T0 = 0、T1 = 1。
- 27ch を T0 と T1 で 15 秒ずつ、各 3 回: **6 回とも TEI 0、CC エラー 0**。パケット数は 8192 × 20 − 312(開始直後に捨てる 312 パケット)。
- 2 チューナーで同時に 60 秒(T0 は 27ch、T1 は 26ch): TEI 0。CC エラーは T0 が 0、T1 が 2(開始から約 36.9 s、映像 PID の連続する 2 パケット。バッファ境界とも開始直後とも無関係で、受信による単発の欠落と考えられる)。
- Mirakurun 4.1.5 + recisdb 1.3.0 経由(B-CAS 復号): 27ch × 2 回と 25ch × 1 回で、TEI 0、CC エラー 0、平文。Mirakurun のエラー数はすべて 0。

### 開始直後の欠落(このブランチで対処)

`start_skip` を入れる前のビルド(既定の ping-pong、8192 パケット)では、27ch を 30 秒ずつ録画すると、T0 と T1 の両方で先頭 5〜61 パケット目に CC エラーが 3 件ずつあり、その後は 0 件だった。別の回では出ないこともあった(ときどき起きる)。DMA を起動する前からブリッジに残っていたパケットと考えられる。ポートの起動直後の 312 パケットを捨てるようにしてからは、上記のとおり出ていない。

## DMA 方式の比較(DMA の取りこぼしは見られない)

ドライバ内のコメントには、ping-pong の再アームで「バッファ境界ごとに多重化 1 周期分を失う
(312 パケットで 2.9%、8192 で 0.30%)」とある。この実機では再現しなかった(27ch、各 30 秒、T0 と T1)。

| DMA の扱い | バッファ | CC エラー |
|---|---|---|
| 既定(ping-pong) | 8192 パケット × 2 | 0 / 0 |
| 既定(ping-pong) | 312 パケット(nbuf は自動で 8) | 0 / 0 |
| 試験的に作った方式: アドレスを書き換えずに同じバッファを再アーム(PX-Q3PE ドライバと同じ) | 312 パケット × 1 | 0 / 0 |

- 再アーム方式でも、ポート 1 の ch0 と ch1 の IRQ は厳密に交互に来た(ブリッジが 2 チャネルを交互に使う)。
- どの方式でも差が出ないため、このブランチでは DMA 方式を変えていない。

## 鍵(pxw3pe.fw)

| `asv5220_dtv.ko` | 結果 |
|---|---|
| 2013-04-23 ビルド(sha256 `402c8fd8…0d99`、`PX-W3PE_LinuxDriver_ver.1.0.0.zip` の中) | 復号した PAT は `00 00 b0 1d 7f e0 …`(TSID 0x7FE0)で CRC32 が一致。TS 全体の PAT/PMT が平文になり、recisdb で B-CAS の復号もできた |
| 2013-01-31 ビルド(sha256 `e8772c62…8a0a`、`px-w3pe/64bit.tar.gz`) | シードは同じだが、DES 鍵 2 本と XOR シードが異なる。PAT の詰め物(0xFF)が復元できない |

- 暗号文の観察: PAT の詰め物の部分は 8 バイト単位で同じ値が繰り返し、ペイロードの 128 バイト目で別の値に切り替わる(ECB、even/odd 鍵の切り替え位置と一致)。CC が違う同じ PAT は同じ暗号文になる。
- ゲートのシード(ASIE の reg 0x10〜0x1F)を変えると暗号文が変わる。

## C/N

- `cn_raw_to_cdb()` の表の値は、PX-Q3PE ドライバの ISDB-T の多項式と、表の点で一致する。
- 補間の小数部は ×100 が正しい(×10 だと、7.3 dB が 7.03 dB と表示される)。
- ロックした直後は C/N のレジスタがまだ更新されていない(約 0.4 秒で落ち着く)。

## 受信品質の参考

- 27/26/25ch は CC 0。24ch と 21ch(C/N 約 17.5 dB)では、TEI 0 のまま 10 秒で約 260 件の CC 欠落があった。ビットレートとは相関しない(受信品質による可能性が高い。未確定)。

## 地デジの受信感度(FC0012 の LNA ゲイン)

FC0012 の reg 0x13(LNA ゲイン)を、High(0x10、変更前の値)から Middle(0x08、mainline の
`fc0012_init()` と同じ値)に変えた。同じカード、同じ日に続けて測定(adapter0、各 10 秒)。

| ch | C/N(High) | C/N(Middle) | CC エラー(High → Middle) |
|---|---|---|---|
| 27 | 19.11 dB | 28.95 dB | 0 → 0 |
| 26 | 18.62 dB | 27.52 dB | 0 → 0 |
| 25 | 18.55 dB | 28.20 dB | 0 → 0 |
| 24 | 17.92 dB | 27.42 dB | 577 → 0 |
| 23 | 18.19 dB | 28.07 dB | 64 → 0 |
| 22 | 18.13 dB | 27.71 dB | 104 → 0 |
| 21 | 17.75 dB | 26.86 dB | 657 → 0 |

- TEI はどちらでも 0。デモジュレータは、訂正できないパケットを TEI を付けずに捨てるので、症状は CC の欠落だけだった。
- 同じアンテナ線につないだテレビでは、エラーは出ていなかった。
- Middle で UHF 13〜62ch を走査すると、13、15、18、19、20、21〜27ch がロックした(C/N は 26〜29 dB)。
- reg 0x0c(0xf8、mainline は 0xfc)と reg 0x12(0x1b、mainline は 0x1f)も mainline と違うが、今回の症状には関係しなかったので変えていない。

## Rocky Linux 10.2 での再現確認(2026-10-17)

上の測定は Ubuntu 24.04 の実機で行ったもの。同じ修正が Rocky 10.2 の実機でも効くか確認した。

- 環境: PX-W3PE Rev1.3(標準レイアウト)、Rocky Linux 10.2、kernel 6.12.0-211.62.1.el10_2、recisdb 1.3.0、
  Mirakurun 4.1.5。Mirakurun は測定中だけ停止した。地デジは強電界で、`recisdb checksignal` の C/N は
  38〜46 dB だった。45.78 dB で変わらないチャンネルは、C/N の表の上限に張り付いているとみられる
- 測定: T0(adapter2)で 14、15、16、17、23、26、29、31ch を 15 秒ずつ、26ch はさらに 2 回、計 10 本。
  `tools/dvbtest.py` で取り込み、`tscheck.py` で集計

| | 取り込み前(`main`) | 取り込み後 |
|---|---|---|
| TEI | 全 10 本で 0 | 全 10 本で 0 |
| CC エラー | 10 本中 9 本で 1〜3 件(合計 15 件) | 全 10 本で 0 |

- 強電界なので、LNA ゲイン(High → Middle)の効果は C/N に出なかった(14ch は 38 → 45 dB、23ch は 43 → 40 dB)。
  CC の改善は、録画開始直後の欠落への対処(`start_skip`)によると考えられる。ただし欠落の位置は記録しておらず、
  修正ごとの寄与は切り分けていない。
- BS/CS(取り込み後): BS15_0 を 15 秒 × 2 回、CS2 を 15 秒 × 1 回録画して、TEI 0、CC エラー 0。
  S0(BS15_0)、S1(CS2)、T0(26ch)、T1(23ch)の 4 本を同時に 20 秒録画しても、全て TEI 0、CC エラー 0。
- BS1_0(TSID 16400)と BS23_0(TSID 18288)は、取り込み前も後も 0 バイトで録画できなかった(BS3_0 は取り込み前後とも録画できた)。
  原因は受信レベルだった(次の節)。

### BS/CS の C/N と録画の可否(2026-10-17)

BS1_0 が 0 バイトになる件を、ドライバの動的デバッグ(`dyndbg`)で調べた。BS1_0 も BS23_0 も、キャリアのロックと TSID の確定は
成功していた。違いは C/N だった。

| 状態 | BS1 | BS3 | BS9〜BS15 | BS21 | BS23 | CS20 | 録画できなかったもの |
|---|---|---|---|---|---|---|---|
| アンテナ線の調整前(adapter0) | 3.1 dB | 6.9 dB | 10.3〜10.8 dB | 7.1 dB | 5.0 dB | 2.3 dB | BS1、BS23 |
| 調整後(adapter0 / adapter1) | 8.8 / 8.9 dB | 9.8 / 10.0 dB | 12.2〜12.3 dB | 12.1 / 12.0 dB | 11.4 / 11.5 dB | 7.0 / 6.9 dB | なし |

- 調整前は、BS の中心(BS13〜BS15)が最も強く、両端に向かって C/N が下がっていた。adapter0 と adapter1 でほぼ同じ値だった。
- BS1 と BS23 は、調整前は C/N が 3〜5 dB でキャリアはロックしたが、データが 1 パケットも来なかった。recisdb 1.3.0 は、
  データが来ないと録画の終了時間を過ぎても止まらない。BS3 は 6.0〜6.9 dB で録画できたが、adapter1 では不安定だった。
- アンテナ線を調整すると全チャンネルの C/N が 2〜6 dB 上がり、BS1_0 と BS23_0 を含めて 10 秒録画できた(約 20MB と約 14MB)。
- 取り込み前の `main` のモジュールでも、調整前の BS1_0 は同じく 0 バイトだった。ドライバの修正による回帰ではなく、受信レベルの問題だった。
- 目安として、C/N が 6 dB 前後を下回ると、キャリアはロックしても録画できないことがある。BS が映らないときは、
  録画の失敗をドライバのせいにする前に、`pxw3pe` の動的デバッグか `recisdb checksignal` で C/N を確認するとよい。
